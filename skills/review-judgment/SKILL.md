# 코드리뷰: 의심을 검증한 뒤 말하기

리뷰는 지적의 개수를 늘리는 일이 아니다. 변경을 받아들였을 때 어떤 동작이 달라지는지 확인하고, 수정할 가치가 있는 문제만 전달한다. 문제가 없다는 결론도 가능하다. 확실히 본 사실, 코드에서 추론한 위험, 확인하지 못한 조건을 섞지 않는다.

## 시작: 변경의 경계부터 확정한다

1. 요청된 범위, PR의 목적, 기준 브랜치와 대상 커밋을 확인한다. 모르면 임의로 `main`을 기준으로 삼지 않는다.
2. 변경 파일 목록과 전체 diff를 대조한다. 큰 diff가 도구 출력에서 잘렸다면 빠진 파일을 따로 연다. 이동·삭제된 파일도 포함한다.
3. 변경 전 구현과 호출부를 읽는다. 새 메서드가 어느 경로에서 호출되는지, 기존 메서드가 남아 있는지 확인한다.
4. 같은 계층의 기존 구현, 테스트, 요구사항, 저장소 규칙을 비교한다. 요구사항을 볼 수 없다면 제품 정책을 추측하지 않는다.
5. 먼저 이번 변경 때문에 생긴 문제인지 확인한다. 원래 있던 문제는 변경으로 악화된 경우가 아니라면 별도로 표시한다.

로컬 저장소에서 어떤 명령으로 조사할지와 잘린 diff·미확인 조건을 다루는 법은 [조사 절차](references/investigate.md)를 따른다. 이 파일은 리뷰를 시작할 때 읽는다.

## 실행 경로를 따라 검증한다

각 변경에 대해 `입력 → 호출부 → 변경 코드 → 저장소/외부 시스템 → 응답`을 따라간다. 함수 이름만으로 DB 접근, 캐시 적중, 트랜잭션 적용을 단정하지 않는다. 의심이 생기면 반례도 찾는다. 예컨대 반복문 속 `find`가 실제 쿼리인지, 이미 한 번에 가져온 데이터를 메모리에서 찾는지 구현을 확인한다.

우선순위는 다음과 같다.

- **동작과 데이터**: 빈 값, 중복·동시 요청, 실패 후 재시도에서 잘못 저장하거나 잘못 응답하는가? 트랜잭션과 유일성 제약이 의도한 불변식을 지키는가?
- **권한과 노출**: 조회·수정 경로마다 권한을 확인하는가? 개인정보나 비밀값이 응답·로그·설정에 새로 드러나는가?
- **부하와 장애**: 데이터가 늘면 쿼리·외부 요청이 입력 개수에 따라 늘어나는가? 조회 범위, 인덱스, 락 유지 시간, 타임아웃·재시도를 확인했는가?
- **중복과 잔여 코드**: 저장소·프레임워크가 이미 제공하는 기능을 다시 만들었는가? 비슷한 책임의 메서드가 둘이 되었는가? 이번 변경으로 미사용 코드가 생겼는가?
- **유지보수와 배포**: 이름과 동작이 일치하는가? 필요 없는 방어 코드·필드·분기가 추가되었는가? 스키마·설정 변경은 이전 버전과 함께 배포되어도 안전한가?

백엔드·DB·외부 API가 걸린 변경이면 [백엔드 검증 기준](references/backend-checks.md)에서 해당 항목을 읽는다. 모든 항목을 기계적으로 적용하지 말고, 변경이 실제로 건드린 위험만 검증한다.

## 리뷰 의견으로 남길지 결정한다

후보마다 아래 질문에 답한다.

1. **조건**: 어떤 입력·상태·동시성·데이터 규모에서 나타나는가?
2. **근거**: 그 조건과 실행 경로를 코드·테스트·설정·문서 중 어디에서 확인했는가?
3. **영향**: 사용자 결과, 데이터, 장애 대응, 유지 비용 중 무엇이 달라지는가?
4. **범위**: 이번 변경이 만들었거나 악화했는가? 지금 고쳐야 하는가?
5. **대안**: 더 작은 수정이나 이미 있는 기능으로 해결할 수 있는가?

조건이나 근거가 비어 있으면 단정하지 않는다. 확인 가능한 질문으로 바꾸거나, 영향이 작고 검증할 길이 없다면 지적하지 않는다. 반대로 데이터 손실·권한 누락처럼 근거가 명확한 문제는 애매한 질문 뒤에 숨기지 않는다. 같은 원인의 여러 위치는 한 의견으로 묶는다. 포매팅처럼 자동 도구가 맡는 일과 개인 취향은 제외한다.

판단과 문장 작성의 실제 예시는 [가상 리뷰 사례](references/comment-examples.md)를 따른다. 예시는 설명을 위한 가상 코드이며 실제 프로젝트의 이력이 아니다.

## 결과를 전달한다

영향이 큰 항목부터 파일·위치와 함께 적는다. 각 항목은 `발생 조건 → 확인한 근거 → 영향 → 제안 또는 질문`이 읽히도록 짧게 쓴다. 확실성에 맞는 표현을 쓴다.

- **확인한 문제**: 무엇이 실제로 잘못되는지 명확히 말하고 수정 방향을 제안한다.
- **의도가 불명확한 문제**: 확인한 사실을 먼저 적고, 필요한 제품 정책이나 설계 의도를 묻는다.
- **검증하지 못한 위험**: 추론이라고 밝히고 어떤 코드·테스트·환경 확인이 필요한지 적는다. 심각도를 확정하지 않는다.

문제가 없다면 `확인한 범위에서는 고쳐야 할 문제를 찾지 못했습니다`라고 말하고, 확인 범위와 실행한 테스트를 적는다. 요구사항을 못 보거나 테스트를 실행하지 못했으면 그 한계를 함께 밝힌다. GitHub에 리뷰를 등록하거나 승인·머지하는 행동은 사용자가 요청한 범위에서만 한다.
