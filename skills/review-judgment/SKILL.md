# 코드리뷰

리뷰의 목적은 지적을 많이 만드는 것이 아니라, 변경을 안전하게 받아들일 수 있는지 판단하는 것이다. 문제가 없으면 없다고 말한다. 확인하지 못한 범위도 함께 밝힌다.

## 1. 변경 전후와 주변 코드를 읽는다

1. PR의 목적과 변경 파일 전체를 확인한다. 파일 목록이나 diff가 잘리지 않았는지 실제 개수와 대조한다.
2. 변경 전 코드와 호출부를 읽는다. 새 파일이 생겼다면 같은 역할을 하는 기존 파일을 찾아 이름, 예외 처리, 데이터 조립 방식이 다른지 본다.
3. 관련 요구사항과 프로젝트 규칙이 있으면 현재 문서를 확인한다. 문서가 없으면 없다고 밝히고 제품 정책을 짐작하지 않는다.
4. 필요하면 커밋 이력을 읽어 기존 코드가 왜 그렇게 작성됐는지 확인한다. 이번 변경이 만든 문제와 이전부터 있던 문제를 구분한다.

diff 한 줄만 보고 결론을 내리지 않는다. 확인에 필요한 코드나 요구사항을 열 수 없다면 검토 범위를 좁혀서 보고한다.

## 2. 먼저 놓치면 안 되는 문제를 확인한다

- **정확성과 데이터**: 정상 입력·빈 값·중복 요청·동시 요청에서 값이 잘못 저장되거나 사라지는가? 트랜잭션 경계가 의도한 작업 전체를 감싸는가?
- **개인정보와 비밀값**: 응답·로그·코드에 노출되는가? 권한 확인이 빠지는 경로가 있는가?
- **부하와 장애**: 반복문에서 DB나 외부 서비스를 원소마다 호출하는가? 조회 범위에 상한과 필요한 인덱스가 있는가? 외부 호출의 실패와 지연을 어떻게 처리하는가?
- **기존 기능과의 중복**: 저장소·프레임워크가 이미 하는 일을 새로 구현했는가? 비슷한 메서드나 엔드포인트가 하나 더 생겼는가?
- **남는 코드**: 이번 변경으로 쓰이지 않게 된 메서드·필드·설정·주석이 있는가? 사용처를 확인한 뒤 지적한다.

여기서 의심이 생겨도 확인한 사실과 추측을 구분한다. 예를 들어 반복 호출을 지적할 때는 반복문과 그 안에서 호출되는 조회 함수를 함께 확인한다. 프레임워크 기능이 있을 것 같다면 사용하는 버전의 공식 문서나 프로젝트 사용 예를 먼저 찾는다.

## 3. 그다음 유지보수와 운영을 본다

- 이름이 실제 동작과 맞는지, 같은 저장소에서 이미 쓰는 관례와 맞는지 본다.
- 실패했을 때 복구에 필요한 로그가 남는지, 같은 정보를 중복 기록하지는 않는지 본다.
- 새 조건과 경계값에 대한 테스트가 있는지 본다. 테스트가 없어도 무엇을 검증해야 하는지 구체적으로 말한다.
- 새 기능이 이 서비스의 역할에 맞는지, 기존 기능을 활용하면 변경 파일과 실행 경로를 줄일 수 있는지 묻는다.
- 새 컬럼·필드·방어 코드가 지금 필요한지 확인한다. 드문 실패를 막기 위해 추가한 코드라면 실패의 영향과 유지 비용을 함께 묻는다.
- 스키마·설정·외부 의존이 바뀌었다면 배포 순서와 이전 버전의 동작을 확인한다.
- 설명 없이는 의도를 알기 어려운 값과 정책은 근거 문서나 짧은 주석을 요청한다.

포매팅과 import 순서처럼 도구가 확인하는 일은 반복해서 지적하지 않는다. 프로젝트의 기존 규칙을 개인 취향보다 우선한다.

## 4. 지적할 내용을 고른다

실제 동작이나 유지보수에 영향을 주는 것부터 남긴다. 같은 원인의 문제가 여러 줄에 있으면 한 건으로 묶고 위치를 적는다. 변경 범위 밖의 문제라면 그 사실을 표시하고, 이번 PR에서 고쳐야 하는 이유가 없으면 별도 작업으로 제안한다.

각 지적에는 다음을 담는다.

1. 문제가 생기는 조건과 영향을 말한다.
2. 코드·테스트·설정·요구사항 중 직접 확인한 근거를 가리킨다.
3. 고칠 방법이 분명하면 짧게 제안한다. 의도나 사실이 불확실하면 확인할 질문을 남긴다.

예: `주문을 하나씩 처리할 때마다 상품을 조회합니다. 주문 수만큼 쿼리가 늘어나므로 식별자를 모아 한 번에 조회할 수 있을까요?`

문제를 확정하지 못한 채 심각도를 매기거나, 근거 없는 가능성만 길게 나열하지 않는다. 상대가 바로 판단할 수 있는 문장으로 쓴다.

## 5. 결과를 보고한다

- 고쳐야 할 문제가 있으면 영향이 큰 순서로 적고, 각 항목의 파일과 위치를 가리킨다.
- 문제가 없으면 `확인한 범위에서는 고쳐야 할 문제를 찾지 못했습니다`라고 말한다. 어떤 부분을 봤고 어떤 테스트를 실행했는지도 적는다.
- 테스트를 실행하지 못했거나 요구사항을 확인하지 못했으면 그 범위를 밝힌다.
- 리뷰 결과를 먼저 대화로 보여 준다. GitHub에 리뷰를 등록하거나 승인·머지하는 행동은 사용자의 지시와 승인을 받은 뒤에 한다.
