# 변경을 조사하는 순서

아래 명령은 로컬 Git 저장소의 예시다. `BASE`와 `HEAD`는 실제 리뷰 대상에 맞게 먼저 결정한다. PR 설명이나 작업 지시와 저장소 상태가 다르면 그 차이를 확인한다. 파일 경로나 검색어는 대상 프로젝트에 맞춰 바꾼다.

## 변경 범위

```bash
git status --short
git diff --name-status BASE...HEAD
git diff --stat BASE...HEAD
git diff --find-renames BASE...HEAD -- path/to/file
```

`BASE...HEAD`는 두 지점의 공통 조상 이후 변경을 보는 PR형 비교다. 작업 트리의 미커밋 변경은 여기 포함되지 않으므로 `git status`와 별도로 확인한다. PR 도구가 보여 주는 diff가 잘렸다면 파일 목록과 각 파일 diff를 다시 대조한다. 생성·삭제·이름 변경도 건너뛰지 않는다.

## 변경 전과 주변 코드

```bash
git merge-base BASE HEAD
git show "$(git merge-base BASE HEAD):path/to/file"
git grep -n 'methodName' HEAD --
git log --oneline -- path/to/file
```

`BASE...HEAD`의 변경 전은 현재 `BASE`가 아니라 공통 조상이다. 기준 브랜치가 분기 뒤 진행되었다면 `git show BASE:path/to/file`은 diff의 변경 전과 달라질 수 있다. 정의만 보지 말고 호출부, 예외 처리, 테스트, 설정을 찾는다. 같은 계층의 기존 구현이 있으면 입력 검증, 트랜잭션, 데이터 조립, 로깅 방식을 비교한다. 이력은 기존 의도를 이해하는 참고자료이지, 현재 동작의 증거를 대신하지 않는다. 프로젝트 지침·요구사항은 접근 가능한 실제 파일에서 확인한다.

## 의심을 가설로 바꾸고 확인한다

예: `목록 크기만큼 조회가 발생한다`는 의심이 있다면 다음을 확인한다.

1. 목록 크기가 입력이나 저장 데이터에 따라 늘어나는가?
2. 반복 안에서 호출된 함수가 매번 DB/네트워크에 접근하는가? 캐시나 사전 로딩이 있는가?
3. 호출 결과가 정말 필요한가? 이미 가져온 데이터로 조립 가능한가?
4. 쿼리 로그·테스트·구현 중 어느 것으로 입증했는가?
5. 묶음 조회 같은 대안이 의미와 권한 필터를 유지하는가?

다른 우려도 같은 식으로 `조건 → 실행 경로 → 관측 가능한 결과 → 반례 → 수정안`을 채운다. 확증이 안 되면 리뷰에 추론이라고 표시한다. 테스트를 실행했다면 명령과 결과를 기록한다. 실행하지 못했다면 통과한 것처럼 쓰지 않는다.

## 범위 밖 문제

변경 전에도 같은 문제가 있었다면 `이번 변경으로 새로 발생한 문제`라고 쓰지 않는다. 변경이 호출 빈도나 노출 범위를 키웠다면 그 차이를 설명한다. 그렇지 않으면 별도 후속 작업으로 분리하고, 이번 PR 차단 의견으로 만들지 않는다.
