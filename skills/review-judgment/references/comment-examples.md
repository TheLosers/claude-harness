# 가상 코드로 보는 판단과 리뷰 의견

다음은 재사용 방법을 설명하기 위한 가상 사례다. 실제 리뷰 이력이나 특정 서비스의 정책을 나타내지 않는다.

## 1. 반복 조회: 구현까지 확인한 뒤 지적

```kotlin
return orders.map { order ->
    val items = itemRepository.findByOrderId(order.id)
    OrderView(order, items)
}
```

확인할 것: `findByOrderId`가 매번 DB 쿼리를 실행하는지, 주문 목록의 상한이 있는지, 이미 항목을 함께 읽는 경로가 있는지. 한 번의 조회 결과를 메모리에서 찾는 함수라면 이 코드만으로 N+1이라고 쓰지 않는다.

확인 후 의견: `주문 목록의 각 항목에서 항목 조회 쿼리가 한 번씩 실행됩니다. 목록이 커질수록 조회 횟수가 늘어나므로 주문 ID를 모아 묶음 조회하고 결과를 ID별로 조립할 수 있을까요?`

나쁜 의견: `N+1 같습니다. 최적화해 주세요.` 조건과 근거가 없다.

## 2. 경쟁 요청: 스키마가 결론을 바꾼다

```kotlin
if (!subscriptionRepository.exists(userId, topicId)) {
    subscriptionRepository.insert(userId, topicId)
}
```

확인할 것: `(userId, topicId)`의 유일성 제약, insert 충돌 처리, 메서드의 호출 경로. 유일성 제약이 있고 충돌을 의도한 응답으로 바꾸면 데이터 중복은 막을 수 있다. 제약이 없다면 두 요청이 모두 `exists == false`를 보고 삽입할 수 있다.

제약이 없음을 확인한 의견: `같은 사용자의 동시 요청이 모두 존재 확인을 통과하면 중복 구독이 저장될 수 있습니다. DB 유일성 제약을 두고 충돌을 처리해야 합니다.`

스키마를 못 본 경우: `존재 확인과 삽입 사이에 경쟁 요청이 들어올 수 있습니다. 이 조합에 유일성 제약이 있거나 삽입 충돌을 처리하는 경로가 있을까요?` 확정된 결함처럼 쓰지 않는다.

## 3. 기존 기능 재사용: 의미가 같은지 먼저 비교

새 만료 작업이 추가되었다고 해서 곧바로 `기존 기능을 쓰세요`라고 말하지 않는다. 저장소나 외부 서비스의 수명주기 기능이 같은 삭제 기준·시점·예외를 제공하는지 확인한다. 의미가 같고 새 작업이 스케줄러·설정·모니터링을 늘린다면 다음처럼 묻는다.

`현재 만료 기준이 기존 수명주기 설정과 같아 보입니다. 이 작업을 별도로 유지해야 하는 이유가 있을까요? 기존 설정으로 처리할 수 있다면 두 경로가 어긋날 위험을 줄일 수 있습니다.`

정책상 즉시 삭제와 지연 삭제가 다르다면 중복이 아니다. 이름이 비슷하다는 이유로 삭제를 요구하지 않는다.

## 4. 요구사항이 없으면 판단을 보류

요청에 `status`가 없을 때 새 코드가 기본값을 `ACTIVE`로 정한다고 하자. 기존 API는 `PENDING`을 사용한다. 정책 문서가 없으면 어느 쪽이 정답인지 알 수 없다.

`기존 생성 경로는 상태가 없을 때 PENDING으로 저장하지만, 새 경로는 ACTIVE로 저장합니다. 두 경로의 정책이 달라야 하는지 확인 부탁드립니다.`

정책 차이를 확정 오류로 단정하지 않는다. 요구사항을 확인한 뒤 수정 필요 여부를 판단한다.

## 5. 외부 호출 재시도: 실패보다 중복 성공을 확인

결제 요청이 타임아웃됐을 때 같은 요청을 재시도하는 코드가 추가되었다고 하자. 첫 요청은 외부 시스템에서 성공했지만 응답만 유실되었을 수 있다. 재시도 횟수만 보지 말고 멱등 키가 두 요청에 동일하게 전달되는지, 외부 API가 그 키를 보장하는지, 최종 상태를 어떻게 확인하는지 조사한다.

보장이 없음을 확인한 의견: `첫 결제 요청이 처리된 뒤 응답만 타임아웃되면, 이 재시도가 같은 결제를 다시 만들 수 있습니다. 외부 API의 멱등성 보장 아래 같은 키를 재사용해야 합니다. 그런 보장이 없다면 처리 상태를 확정하기 전 자동 재시도를 하지 않아야 합니다.`

반대로 외부 API가 같은 키의 중복 처리를 보장하고 코드가 같은 키를 재사용한다면, 타임아웃 뒤 재시도만으로 결함이라고 하지 않는다.

## 6. 권한 검사: 호출 위치보다 우회 경로를 확인

상세 조회 핸들러에 권한 검사가 보이지 않아도 공통 미들웨어가 검사할 수 있다. 반대로 목록 API에서 필터를 적용했다는 이유로 개별 ID 조회가 안전해지는 것은 아니다. 실제 요청 경로에서 객체 소유자 또는 접근 권한을 어디서 확인하는지 따라간다.

우회 경로를 확인한 의견: `목록 조회에는 사용자 조건이 적용되지만 이 ID 조회는 해당 조건 없이 객체를 반환합니다. 다른 사용자의 ID를 전달하면 상세 정보를 읽을 수 있으므로 같은 권한 조건을 적용해야 합니다.`

미들웨어를 보지 못했다면 `권한 검사가 없다`고 확정하지 말고, 어떤 계층에서 검사가 이루어지는지 확인할 질문으로 남긴다.

## 7. 테스트 요청: 빠진 동작을 지정

`테스트가 없습니다`만으로는 무엇을 추가해야 할지 알기 어렵다. 변경한 분기가 실패할 수 있는 조건을 찾고, 기대 결과를 명시한다.

예: `중복 구독 요청이 동시에 들어와도 한 건만 남고, 두 번째 요청이 정의된 충돌 응답을 반환하는 테스트가 필요합니다.`

이미 DB 제약과 통합 테스트가 이 조건을 검증한다면 새 테스트를 요구하지 않는다. 테스트를 못 실행했다면 그 사실을 보고하고 통과 여부를 추정하지 않는다.

## 결과 형태

```text
확인한 문제
- path/to/File.kt:42 — [조건]일 때 [잘못된 결과]가 발생합니다. [확인한 근거]. [작은 수정 제안].

확인 범위
- 변경 파일과 관련 호출부, 테스트를 확인했습니다.
- [실행한 테스트와 결과 또는 실행하지 못한 이유].
- [보지 못한 요구사항·환경·스키마가 있다면 명시].
```

의견이 없다면 문제 목록을 억지로 채우지 않는다. `확인한 범위에서는 고쳐야 할 문제를 찾지 못했습니다`와 실제 확인 범위를 적는다. 결과를 대화로 먼저 보여 주고, 외부 서비스에 리뷰를 올리는 일은 별도 요청을 따른다.
