# 백엔드 변경 검증 기준

체크리스트는 결론이 아니다. 해당 변경이 건드린 실행 경로만 고르고, 의심을 뒷받침하는 코드·스키마·테스트·설정을 찾는다.

| 변경 신호 | 확인할 것 | 의견으로 남길 조건 |
| --- | --- | --- |
| 목록을 순회하며 저장소 메서드 호출 | 저장소 구현이 매번 쿼리하는지, 목록 상한·배치 API·사전 로딩이 있는지 | 입력이 늘면 쿼리/외부 호출도 비례해서 늘고, 그 영향이 실제로 문제일 때. 묶음 처리는 가능한 수정안인지 별도 확인 |
| 조회 조건·정렬·페이지 추가 | 실제 조회 상한, 필요한 인덱스, 정렬 안정성, 권한 조건이 쿼리에도 적용되는지 | 큰 데이터에서 무제한 조회가 가능하거나 페이지 경계에서 누락·중복이 생길 때 |
| `exists` 다음 `insert` 같은 두 단계 처리 | 유일성 제약, 경쟁 요청, 트랜잭션/락, 충돌 시 응답 | 동시 요청이 둘 다 통과할 수 있는데 DB가 불변식을 막지 못할 때 |
| 여러 쓰기 또는 이벤트 발행 | 트랜잭션 범위, 실패 중간 상태, 이벤트와 DB 커밋의 순서 | 부분 성공 후 데이터가 어긋나고 재시도도 안전하지 않을 때 |
| 외부 API 호출 | 타임아웃, 재시도 가능 오류, 멱등성, 실패 응답, 자원 점유 | 요청이 무기한 묶이거나 재시도로 중복 작업이 생길 때 |
| 권한 있는 데이터 접근 | 객체 단위 권한, 간접 조회 경로, 캐시 키의 사용자 범위 | 다른 사용자 데이터를 읽거나 갱신할 수 있는 경로가 있을 때 |
| 로그·응답 필드 추가 | 비밀값/개인정보, 예외에 포함된 원문, 장애 조사에 필요한 식별자 | 새 노출이 생기거나 실패 원인을 찾을 근거가 사라질 때 |
| 스키마·설정 변경 | 이전/새 버전의 동시 실행, 기본값, 백필, 롤백 가능성 | 배포 순서에 따라 기존 코드가 실패하거나 데이터 해석이 바뀔 때 |
| 메서드·필드·서비스 추가 | 같은 책임의 기존 구현, 프레임워크 기능, 새 코드의 실제 사용처 | 의미가 같은 경로가 둘 생겨 이후 수정이 한쪽에만 적용될 때 |

## 결정할 때 주의할 점

- 호출 이름만으로 N+1을 판정하지 않는다. 실제 I/O가 있는지 본다. 반대로 메서드가 한 번 호출되어도 내부에서 목록만큼 조회하면 문제를 놓치지 않는다.
- `@Transactional` 같은 표지만 보고 원자성을 보장하지 않는다. 호출 경계, 예외 처리, 별도 프로세스의 작업을 확인한다. DB 제약이 필요한 불변식은 애플리케이션 검사만으로 보장한다고 단정하지 않는다.
- 느릴 *수 있다*는 말 대신 입력 규모와 호출 수가 어떻게 연결되는지 설명한다. 측정치가 없다면 시간을 꾸며 내지 않는다.
- 기존 라이브러리 기능을 대안으로 제안하기 전 사용 버전과 의미가 맞는지 확인한다. 의도가 다른 기능을 이름만 보고 중복이라고 하지 않는다.
- 방어 코드가 많다는 이유만으로 삭제를 요구하지 않는다. 방어 대상의 실패 가능성·영향과 코드 유지 비용을 함께 본다.
- 테스트 부재 자체보다 빠진 동작을 말한다. 예를 들어 `중복 요청에서 한 건만 저장되는지`처럼 검증할 조건을 지정한다.
