# 지목받은 것만 커밋하고 푸시한다

> **「이거 푸시해 줘」는 그것만 푸시하라는 뜻이다.**

푸시 자체를 막는 규칙이 아니다. 커밋·푸시 전에 허가를 다시 묻지 않는다.
이 규칙이 통제하는 것은 **무엇을 올리는가**다.

- 같은 작업에서 나온 파일이라도, 관례상 그 위치가 맞더라도, 지목받지 않았으면 넣지 않는다
- 함께 올리는 게 낫다고 판단되면 **올리기 전에** 파일 목록을 보여 주고 묻는다. 올린 뒤에 통보하지 않는다
- `git add` 는 지목받은 경로만 쓴다. `git add -A`, `git add .` 로 쓸어 담지 않는다
- 남이 커밋하지 않은 변경을 내 커밋에 넣지 않는다. 작업 트리가 지저분하면 변경의 소유와 범위를 먼저 확인한다
- 내가 만든 산출물(리뷰 결과, 조사 자료, 임시 문서)은 기본이 로컬이다. 저장소에 남길지는 사용자가 정한다

## 파일을 지워도 공개 이력은 남는다

지운 커밋을 올려도 히스토리에는 그대로 남는다. `git show <sha>:<path>` 로 누구나 읽을 수 있고 웹 화면에서도 보인다.
「지웠습니다」는 노출이 끝났다는 뜻이 아니다. 히스토리를 다시 써도 이미 받은 복사본까지 회수할 수는 없다.
그래서 무엇을 담는지는 올리기 전에 정한다. 비밀값이 노출됐다면 파일 삭제와 별개로 해당 값을 폐기하거나 교체해야 한다.

## 이유

「RFC 를 초안 상태로 푸시해 줘」라는 지시에, RFC 와 함께 요청받지 않은 파일 둘을 묶어 올렸다.
하나는 내가 돌린 리뷰 결과였고, 하나는 사용자 개인 폴더에 있던 조사 자료였다. 사내 저장소에 하루 가까이 남았고,
지운 뒤에도 히스토리에는 남았다. 게다가 함께 올린 근거가 내가 만든 리뷰의 지적이었다.
내 산출물이 내 행동을 정당화하는 고리가 생겼고, 그 안에 사용자가 없었다.

이 사고의 먼저 고칠 원인은 [리뷰와 문서 작성의 구분](review-is-not-a-document.md)에 있다.
