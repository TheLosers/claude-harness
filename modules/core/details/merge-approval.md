# 머지와 PR 리뷰 등록은 매번 승인받는다

> **`gh pr merge` 와 `gh pr review` 는 사용자 승인 없이 실행하지 않는다. 매번 받는다.**

푸시는 브랜치에 쌓는 일이라 되돌리기 쉽다. 머지는 공유 브랜치에 들어가 다른 사람의 작업과 배포에 바로 영향을 준다.
리뷰 등록은 리뷰받는 사람이 곧바로 읽는다. 맥락에 맞지 않는 지적이 올라가면 혼선을 준다.

## 머지

- 「머지해 줘」라고 들었을 때만 머지한다. 그 말이 없으면 머지할 준비가 됐다고 보고하고 지시를 기다린다
- 간접 표현을 승인으로 바꿔 읽지 않는다. 「완료되면」, 「다 되면」, 「이어서 해 줘」는 머지 허가가 아니다. 무엇이 완료인지는 사용자가 정한다
- 리뷰 지적을 반영했다는 것은 머지 사유가 되지 않는다. 반영이 맞는지 판단하는 사람은 리뷰어다. 변경 요청(`CHANGES_REQUESTED`)이 걸려 있으면 더욱 그렇다
- 여러 PR 을 한 번에 지시받으면 그 목록 안에서만 머지한다. 나중에 생긴 PR 은 새로 승인받는다
- 개인 작업의 기본 머지 방식은 머지 커밋(`gh pr merge --merge`)이다. 저장소 정책이 다르면 그 정책을 먼저 확인한다

## 리뷰 등록

1. 리뷰를 쓴다
2. 사용자에게 그 내용을 먼저 보인다
3. 사용자가 고칠 곳을 말하면 고친다
4. 승인을 받은 뒤에만 등록한다

## 이유

사용자가 「완료되면 테스트 환경에 올려 주고」라고 했다. 나는 그 「완료」를 「머지까지」로 읽고 PR 을 머지했다.
그 PR 에는 리뷰어의 변경 요청이 걸려 있었다. 「그 지적을 그대로 반영한 커밋이니 괜찮다」는 것도 내 판단이었다.
지적을 제대로 반영했는지 판단하는 사람은 리뷰어다. 배포 지시가 머지 지시를 포함한다고 넘겨짚었다.

기계적으로 막는 훅은 `gates` 묶음에 있다.
