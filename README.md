# Claude Harness

Claude Code로 작업하면서 쌓은 규칙과 훅을 관리합니다. 환경이 바뀌어도 가져가서 쓸 수 있도록, 개인 작업 원칙과 회사별 설정을 분리했습니다. 각 규칙이 생긴 이유와 시행착오도 함께 남깁니다.

여기서 **하네스**는 AI가 코드를 쓰는 주변 환경을 뜻합니다. 작업 원칙을 읽히는 문서, 도구 실행 전에 확인하는 훅, 그 동작을 확인하는 테스트를 묶었습니다.

## 왜 만들었나

AI와 작업하다 보면 코드의 정답 여부 밖에서도 문제가 생깁니다. 질문만 했는데 파일을 고치거나, 실패한 테스트를 꺼서 통과시키거나, 리뷰를 마친 뒤 머지까지 진행하는 식입니다.

이런 일을 겪을 때마다 지시를 덧붙였습니다. 이후 **짧은 규칙 → 그 규칙을 만든 사례 → 코드로 확인할 수 있는 조건**으로 나눴습니다. 매번 읽힐 내용은 짧게 두고, 판단이 필요한 순간에는 이유를 찾아볼 수 있게 했습니다.

| 겪은 문제 | 정한 원칙 | 확인하는 방법 |
|---|---|---|
| 질문이나 리뷰 요청을 실행 허가로 해석했다 | 답변과 실행을 구분한다 | [사례와 판단 기준](modules/core/details/answer-only.md) |
| 실패한 테스트를 끄고 완료하려 했다 | 실패 원인을 고친다 | [테스트 비활성화 표시 검사](modules/gates/hooks/edit-guard.sh) |
| 리뷰 지적 반영을 머지 허가로 받아들였다 | 대상과 내용을 보이고 매번 승인받는다 | [차단 훅과 일회용 표식](modules/gates/details/why-deny-and-marker.md) |
| 익숙한 설계 용어로 설명해도 상대가 이해하기 어려웠다 | 구체적인 예를 먼저 쓰고 문장을 나눈다 | [고치기 전·후 문장](modules/korean-writing/details/plain-words.md) |

문서 규칙을 모두 코드로 강제하지는 않습니다. 훅이 확인하는 범위와 사람이 판단할 부분을 구분해 둡니다.

## 둘러보기

- [core](modules/core/RULES.md): 요청 범위, 증거, 테스트, 커밋과 머지 원칙
- [korean-writing](modules/korean-writing/RULES.md): 설명을 쉽게 쓰는 법과 실제 문장 교정 사례
- [gates](modules/gates/RULES.md): DB·PR·브라우저·편집 전 확인
- [backend](modules/backend/RULES.md): 반복 조회 방지와 SQL 실행 승인

각 묶음의 `RULES.md`는 짧은 규칙 목록이고, `details/`는 규칙이 생긴 상황과 적용 이유입니다. [CLAUDE.md](CLAUDE.md)가 네 묶음을 불러옵니다. 외부 스킬은 [출처 링크](external-skills.md)만 둡니다.

사례 기록의 ‘나’는 당시 작업하던 AI 에이전트입니다. 에이전트의 행동과 제가 바로잡은 기준을 남기되, 회사와 사람을 알아볼 수 있는 정보는 일반화했습니다.

## 사용하기

필요한 도구는 Git, Bash, jq입니다. 테스트에는 Python 3도 사용합니다. 기존 Claude 설정은 자동으로 덮어쓰지 않습니다.

```bash
git clone https://github.com/TheLosers/claude-harness.git ~/claude-harness
cd ~/claude-harness
python3 -m unittest discover -s tests -p 'test_*.py' -v
bash tests/test-public-scan.sh
```

1. `~/.claude/CLAUDE.md`에 `@~/claude-harness/CLAUDE.md` 한 줄을 추가합니다. 경로가 다르면 바꿉니다.
2. 훅도 쓰려면 [설치 안내](docs/setup.md)를 따라 기존 `~/.claude/settings.json`에 필요한 항목만 합칩니다.
3. 회사별 DB 주소와 공개 금지어는 저장소 밖 `~/.config/claude-harness/`에 둡니다.

규칙 문서만 먼저 쓰고 훅은 나중에 선택해도 됩니다. 이 저장소는 OMC 플러그인이나 외부 스킬을 설치하지 않습니다.

## 무엇을 검증했나

공개판을 준비하면서 가짜 도구 입력으로 **훅 테스트 32개, 공개 검사 테스트 8개**를 통과시켰습니다. 실제 DB 변경, PR 머지, 브라우저 종료는 실행하지 않습니다.

- 차단할 입력과 통과할 입력, 승인 표식의 대상·만료·한 번 사용 후 삭제
- 잘못된 JSON과 jq 누락, 승인 이후에도 남은 게이트를 검사하는지
- 테스트 비활성화 표시와 기존 파일 읽기 기록
- 가짜 비밀값·금지어, 파일을 지워도 Git 이력에 남은 값

검사 중 발견한 잘못된 입력의 통과, 승인 뒤 검사 생략, 읽기 기록의 공백 오인식을 수정하고 회귀 테스트로 남겼습니다. [테스트와 한계](docs/verification.md)에 확인 범위를 적었습니다.

## 한계와 관리 방식

이 훅은 **실수를 줄이는 보조장치**입니다. 셸·SQL의 의미를 전부 해석하지 않고, 승인 표식도 실제 사용자 승인을 인증하지 못합니다. 조직의 권한 관리나 샌드박스를 대신하지 않습니다. 새 환경에서는 설정을 검토하고 Claude Code 안에서 동작을 확인해야 합니다.

새 규칙은 겪은 문제와 이유부터 기록합니다. 코드로 확인할 수 있는 조건은 테스트를 붙입니다. 실제 주소·계정·작업 기록은 공개판에 넣지 않고, 커밋과 푸시 전에 [공개 검사](scripts/check-public.sh)를 돌립니다.

제 작업 방식에 맞춘 개인 설정입니다. 필요한 규칙만 골라 자신의 환경과 승인 정책에 맞게 조정하세요.
